## The sequencing constraint that orders everything

`SOURCE_OWNER_ROSTER` / `SOURCE_OWNER_GLOBS` (`src/fep_lean/output/provenance.py:19-28`,
`OWNER_MANIFEST_VERSION = 15`) bind the **bytes of every `src/fep_lean/**/*.py`
and `scripts/*.py` file**, and `CONFIG_OWNER_FILES` (`provenance.py:125-139`)
binds `pyproject.toml`, `uv.lock`, the lean pins, and the config YAMLs into
report, native, and release receipts. **Any edit to those paths invalidates the
recorded evidence chain** — which is already stale for the bridge pin and the
native digest (see `FEP-EVIDENCE-CURRENT`).

Therefore all work splits into three waves:

- **Wave 1 — receipt-neutral.** `lean/build.sh`, `.github/`, `docs/`, `tests/`,
  `AGENTS.md`/`docs/` prose, and non-`.py` scripts. Zero evidence cost; do all
  of it first.
- **Wave 2 — one coordinated code wave + ONE evidence refresh.** Every
  `src/**` + `scripts/*.py` + `pyproject.toml` change batched together, then a
  single refresh closing `FEP-EVIDENCE-CURRENT`: bridge custody re-pin →
  `fep-lean verify --fail-on-warnings --receipt output/native-verification.json`
  → `scripts/audit_formalisms.py --receipt` → `fep-lean catalogue` +
  render/font receipts → browser capture → `build_release_bundle.py` +
  `verify_report_receipt.py`. Never interleave code edits with the refresh;
  never ship two refreshes for one wave.
- **Wave 3 — externally gated.** Provider run, H3 science, next Lean/Mathlib
  upgrade, CI render lane.
